## 需求背景
海量IPC设备通过WS（WebSocket）网关接入宇视云平台，设备与WS网关之间维持130s的保活心跳机制——若在130s内网关未收到设备的保活消息，则认为设备离线。当前存在以下痛点：

1. **设备夜间不稳定重启**：部分设备夜间概率性重启，短暂离线后自动恢复，此类瞬断离线对用户无实际意义，频繁通知会造成打扰。
2. **WS网关升级/重启**：网关侧升级或重启超过130s时，会导致连接该网关的所有设备批量离线，产生大量离线消息推送给用户，造成告警风暴，严重影响用户体验。

## 需求功能点
1. **设备离线通知**：当设备真实离线时，通过APP推送设备离线通知给用户
2. **短时离线过滤**：设备短暂离线（如夜间重启导致）后快速恢复的场景，不发送离线通知
3. **网关批量离线过滤**：WS网关升级/重启导致的大批量设备同时离线，不发送离线通知给用户
4. **设备上线通知（建议）**：设备离线后重新上线时，推送上线恢复通知，让用户感知设备已恢复

**友商共性**：主流方案均采用"延迟窗口"策略——设备离线后不立即通知，等待一段窗口期，若设备在窗口期内恢复上线则不推送通知。

# 我司方案

## 整体设计思路

### 核心策略：延迟通知 + 分层过滤

```
设备离线事件 → [短时离线过滤层] → [网关批量离线过滤层] → [离线通知下发] → APP推送
```

**第一层：短时离线过滤（延迟窗口机制）**
- 设备离线后不立即发送通知，进入延迟观察期（建议5分钟）
- 延迟观察期内设备重新上线 → 取消通知，不推送
- 延迟观察期结束设备仍离线 → 进入下一层过滤

**第二层：网关批量离线过滤（网关级聚合检测）**
- 检测同一WS网关下是否出现批量设备离线（超过阈值）
- 若为网关级批量离线事件 → 抑制通知，标记为"网关异常"
- 若为单设备/少量设备离线 → 正常下发通知

### 关键参数设计

| 参数 | 建议值 | 说明 | 可配置 |
| --- | --- | --- | --- |
| 离线通知延迟时间 | 5分钟 | 设备离线后等待5分钟再判断是否通知 | 是（云端可配） |
| 网关批量离线阈值 | 单网关5分钟内≥N台设备同时离线 | N值需根据网关平均接入量确定，建议为接入量的10%或绝对值≥10台 | 是（云端可配） |
| 网关离线观察窗口 | 5分钟 | 与离线通知延迟时间对齐，统计窗口内同网关离线设备数 | 是 |

## 详细技术方案

### keepalive服务改造

**1. 离线事件延迟队列**

```
设备保活超时
    → 写入延迟队列（TTL = delayMinutes * 60 * 1000 ms）
    → 同时记录到离线待确认表 {deviceId, gatewayId, offlineTime, status: "pending"}

延迟队列到期消费
    → 查询离线待确认表，状态仍为pending
    → 检查网关批量离线情况
    → 满足条件则下发通知，更新状态为 "notified"

设备重新上线
    → 查询离线待确认表，状态为pending
    → 更新状态为 "cancelled"
    → 延迟队列到期时检查状态，已cancelled则跳过
```

**2. 网关批量离线检测**

```
定期任务（每分钟执行）：
    → 查询最近5分钟内同gatewayId下的pending离线事件数
    → 如果 count >= gatewayBatchThreshold：
        → 将该网关下所有pending事件标记为 "gateway_suppressed"
        → 记录网关异常事件 {gatewayId, suppressTime, affectedDeviceCount}
    → 如果网关异常事件超过可配置时间（如30分钟）仍未恢复：
        → 将suppressed事件重新置为pending，逐个走正常通知流程
```

**3. 网关升级通知联动（建议）**

网关升级前主动上报升级事件：
- 网关升级开始 → 通知keepalive服务，直接将该网关下所有设备标记为 "gateway_upgrade_suppressed"
- 网关升级完成 → 解除抑制，设备自动重连后恢复正常

## 异常场景处理

| 场景 | 处理策略 |
| --- | --- |
| 设备频繁断连重连（反复离线/上线） | 增加防抖机制：同一设备5分钟内只产生1次离线事件，避免通知风暴 |
| keepalive服务重启 | 延迟队列数据持久化到Redis/DB，服务重启后恢复未消费的延迟事件 |
| 通知服务不可用 | 离线事件入队重试，保证最终一致性 |
| 网关长时间不可用（>30分钟） | 超过配置时间后，解除批量抑制，按单设备离线逐个通知 |
| 用户未登录APP | 走系统级推送（APNs/FCM/鸿蒙推送），保证消息触达 |
| 大量设备同时离线（非网关原因） | 如网络故障导致区域性离线，按网关维度聚合检测可能误判，需结合多网关分析 |

## 安全合规设计

1、对外接口是否有增加异常保护，是否有未鉴权等安全风险。

- 离线通知配置接口和消息查询接口需鉴权，仅设备所有者可查询和配置
- 离线事件上报为内部服务间调用，需通过内网鉴权（服务间Token或mTLS）
- 防止恶意大量上报离线事件导致通知炸弹，需增加接口限流

2、是否新增监听TCP/UDP端口、端口和业务接口鉴权安全机制、强密码、敏感信息加密传输和保存、Web应用安全、日志和配置安全。

- 本需求不新增对外监听端口
- 设备离线事件数据不涉及敏感个人信息，但设备名称可能包含用户隐私信息，推送时需脱敏处理（可配置是否展示设备名称）

3、是否新增收集个人信息及隐私政策是否需要更新。

- 设备离线/上线状态属于设备运行数据，不新增个人信息收集
- 但需确认离线通知功能是否需要在隐私政策中声明（通知推送本身可能涉及用户选择权）
- 建议在APP设置中增加"设备离线通知"开关，尊重用户选择
