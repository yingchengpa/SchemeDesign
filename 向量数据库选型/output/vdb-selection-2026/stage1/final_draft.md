# 向量数据库选型技术分析报告

## 一、背景与目标

### 1.1 业务场景

宇视云平台中，IPC/NVR 设备持续上报特征值数据，经向量化后存储于向量数据库中。用户通过文本输入发起检索请求，系统对输入文本进行 Embedding 向量化处理，再通过向量相似度检索匹配目标特征。当前技术方案使用腾讯云向量数据库（Tencent Cloud VectorDB），特征数据全量存储于内存中。

### 1.2 核心痛点

当前全内存模式导致内存使用量过大，云服务成本居高不下。以业务规模持续增长的趋势来看，若不引入磁盘/内存可互换方案，内存成本将线性增长，不具备可持续性。

### 1.3 选型目标

- 支持内存/磁盘可互换的向量存储方案，显著降低内存占用
- 满足国内外多地域部署需求（海外为硬性约束）
- 在成本优化的前提下，保持可接受的查询延迟与召回率
- 控制迁移成本与运维复杂度

## 三、方案详细分析

### 3.1 腾讯云向量数据库 — 开启磁盘索引

**技术概述**

腾讯云向量数据库源自集团自研的向量检索引擎 OLAMA，已提供 DiskFLAT 和 DiskANN 两种磁盘索引类型：

- **DiskFLAT 索引**：保持 100% 召回率的同时，相比全内存方案成本下降 50%-90%，适合对召回率要求极高的场景
- **DiskANN 索引**：在成本与性能之间取得平衡，内存中保留压缩向量用于导航图遍历，原始向量存储在磁盘

**核心优势**

| 维度 | 评估 |
|------|------|
| 迁移成本 | 零迁移 — 当前已在用，仅需切换索引类型 |
| 运维复杂度 | 全托管，零运维 |
| 国内磁盘索引 | 已验证可用，成本节省显著 |
| 内核性能 | HNSW 索引性能提升 50%+，向量量化存储成本降低 50%-75% |

**关键瓶颈**

| 维度 | 评估 |
|------|------|
| 海外部署 | 磁盘索引在海外区域不支持，仅能使用全内存模式 |
| 时间表 | 海外磁盘索引上线时间未公布 |
| 灵活性 | 闭源托管，无法自调参数或扩展 |

**适用判断**：仅国内部署场景下的最优解。海外部署受限为硬伤。

---

### 3.2 阿里云向量检索服务 Milvus 版

**技术概述**

阿里云 Milvus 版基于 Linux Foundation Project Milvus 开发，提供全托管服务。其核心差异化在于对 DiskANN 磁盘索引的全栈深度优化，将 DiskANN 图索引与最前沿的 RaBitQ 量化算法深度融合。

**核心技术：DiskANN + RaBitQ**

1. **Vamana 图内存重排布**：将开源 DiskANN 中与向量数据混放的邻居列表在内存中重新组织，实现搜索过程 Zero I/O，仅在最后 Rerank 阶段从磁盘获取原始向量，彻底消除搜索路径中的随机磁盘 I/O
2. **RaBitQ 量化算法**：通过随机正交变换将向量映射到超立方体顶点，实现从 1bit 到 4bit 的精准压缩。在高维空间中，量化误差以 O(1/√d) 速率收敛，768 维空间下 1-bit 量化误差已极小
3. **4-bit 扩展模式**：在标准 1-bit 基础上扩展 4-bit 残差编码，平衡压缩比与精度

**实测性能（1 亿 768 维标准评测数据集）**

| 指标 | 阿里云优化版 | 开源 Milvus DiskANN | 提升幅度 |
|------|-------------|---------------------|---------|
| QPS | 开源版 20 倍+ | 基准 | 20x+ |
| P99 延迟 | 基准 1/10 以下 | 基准 | 降低 90%+ |
| QueryNode 内存 | 减少约 29% | 基准 | -29% |
| 召回率 | 98%+ | 基准 | 保持 |

**海外支持**

| 区域 | 可用区 |
|------|--------|
| 新加坡 | Zone B, Zone C |
| 德国法兰克福 | Zone A, Zone B |
| 中国香港 | Zone B, Zone C |
| 国内（北京/上海/杭州/深圳/乌兰察布/张家口） | 多可用区 |

**内存成本对比（1 亿 768 维向量为基准）**

| 部署模式 | 理论内存 | 推荐内存（×1.5） | 实例规格建议 |
|---------|---------|----------------|-------------|
| 性能模式（HNSW） | 57 GB | ~85 GB | 2 节点 × 16C64G |
| 磁盘模式（DiskANN） | 36 GB | ~54 GB | 1 节点 × 16C64G |

**核心优势**

- 海外区域支持磁盘索引（新加坡/法兰克福/香港）
- 磁盘向量索引性能业界领先（RaBitQ 优化后 QPS 为开源版 20 倍+）
- 全托管服务，运维成本低
- 提供 AI 中心（Embedding/Rerank/文本生成一站式集成）

**关键风险**

- 需重写接入层（SDK/API 与腾讯 VectorDB 不兼容）
- 数据迁移工程量较大
- 产生双云供应商依赖
- 存储优化型实例版本要求 ≥2.6.18

### 3.3 开源 Milvus（自建）

**技术概述**

开源 Milvus 支持 DiskANN 磁盘索引，将向量数据和图索引存储在 NVMe SSD 上，内存仅保留 PQ 压缩后的导航图，实现内存与磁盘的分离存储。

**成本对比（100M 1536 维向量为基准）**

| 索引类型 | 内存需求 | 月费估算 | 节省比例 |
|---------|---------|---------|---------|
| HNSW（全内存） | 80-90 GB | ~$460 | — |
| DiskANN（NVMe SSD） | 12-16 GB + 500GB NVMe | ~$180 | 61% |

| 数据规模 | HNSW 月费 | DiskANN 月费 | 节省比例 |
|---------|----------|-------------|---------|
| 100M 向量 | $460 | $180 | 61% |
| 250M 向量 | $1,150 | $320 | 72% |
| 500M 向量 | $2,300 | $580 | 75% |
| 1B 向量 | $4,600 | $1,100 | 76% |

**延迟特性**

| 指标 | HNSW（内存） | DiskANN（NVMe SSD） |
|------|-------------|---------------------|
| p50 延迟 | 1-3ms | 3-8ms |
| p99 延迟 | 2-5ms | 5-15ms |
| p999 延迟 | 5-10ms | 15-40ms |

**注意**：以上为阿里云优化版数据。开源版 DiskANN 由于 PQ 查表效率低、I/O 调度开销大、大量候选节点无效计算等问题，实际 P99 延迟通常在 15-40ms 区间。

**运维负担**

开源 Milvus 集群需要管理以下组件：

| 组件 | 职责 |
|------|------|
| etcd | 元数据存储与协调 |
| MinIO | 对象存储（向量数据持久层） |
| MixCoord | 集群协调节点 |
| QueryNode | 查询执行节点 |
| DataNode | 数据写入节点 |
| IndexNode | 索引构建节点 |

冷启动时间约 90 秒（Standalone），集群版更长。

**适用判断**：适合有成熟运维团队的场景，且需要完全自主可控。但开源 DiskANN 性能与阿里云优化版差距显著。

### 3.4 Qdrant（自建）

**技术概述**

Qdrant 是 Rust 实现的高性能向量数据库，其磁盘方案采用 mmap + 量化的组合策略，架构灵活度在所有候选方案中最高。

**Qdrant 1.19 三层内存分级**

| 内存层级 | 行为 | 适用组件 |
|---------|------|---------|
| **pinned** | 全量常驻内存，不被驱逐 | 量化向量副本、HNSW 图 |
| **cached** | 磁盘存储 + 启动时预热页缓存，可被 OS 驱逐 | 原始向量（有足够内存时） |
| **cold** | 磁盘存储 + 按需加载 | 原始向量（内存紧张时） |

**量化压缩方案**

| 量化方法 | 压缩倍数 | 说明 |
|---------|---------|------|
| Scalar Quantization (int8) | 4x | 精度损失小 |
| Binary Quantization | 32x | 高维效果好，支持 XOR+popcount 加速 |
| Product Quantization | 64x | 压缩最强，但精度损失大、非 SIMD 友好 |
| TurboQuant (4-bit) | 8x | 精度与压缩平衡最优 |
| Turbo4 datatype | 9x | 仅存 4-bit 压缩副本，不保留原始向量 |

**实测数据（内存限制 4GB）**

| 配置 | p50 延迟 | 说明 |
|------|---------|------|
| 量化 pinned + 原始 cached + rescore off | 4.3ms | 原始向量在页缓存中 |
| 量化 pinned + 原始 cached + rescore on | 43ms | 需磁盘读取原始向量 |
| 量化 pinned + 原始在页缓存中 + rescore on | ~4ms | 接近全内存性能 |

**核心优势**

- 内存管理最灵活（三层分级 + 可选量化），精细控制每个组件的内存放置
- 单机部署架构简洁（无需 etcd/MinIO 等外部依赖）
- Rust 实现，内存安全性好，运行稳定
- 过滤搜索性能优秀（ACORN 算法，原生 HNSW 图内过滤）
- 多租户支持完善（is_tenant 索引，物理隔离存储）

**关键限制**

- 单机扩展性受限，5000 万+向量需要多节点集群
- 磁盘 rescore 场景下延迟较高（p50 40-50ms）
- 自建需运维，但架构比 Milvus 简洁很多

### 3.5 pgvector（不推荐）

**技术概述**

pgvector 是 PostgreSQL 的向量检索扩展，依赖 PG 的 page cache 实现磁盘到内存的自动缓存。不具备真正的磁盘向量索引。

**性能对比（300 万 1024 维向量，32 核 128G 内存 NVMe SSD，Recall 92%）**

| 指标 | Milvus 2.4 | pgvector 0.7 | Qdrant 1.10 |
|------|-----------|-------------|-------------|
| 稳态 QPS | 780 | 210 | 620 |
| P99 延迟 | 45ms | 180ms | 55ms |
| 冷启动时间 | 90s | 12s | 25s |
| 索引重建时长 | 6 分钟 | 42 分钟 | 4 分钟 |
| 内存占用 | 14 GB | 22 GB | 11 GB |

**不推荐理由**

- 缺少真正的磁盘向量索引，无法实现内存/磁盘可互换
- QPS 仅为 Milvus 的 1/4，索引重建时间 7 倍
- 仅适合"已有 PostgreSQL 且向量仅为附属功能"的场景，不适合向量检索为核心的业务

## 五、决策建议

### 5.1 推荐路径

根据是否有海外部署需求，推荐路径分叉：

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| **仅国内** | 腾讯云 VectorDB 开启磁盘索引 | 零迁移、全托管、DiskFLAT 成本降 50%-90% |
| **国内 + 海外** | 国内：腾讯云 VectorDB 磁盘索引；海外：阿里云 Milvus | 海外唯一的全托管+磁盘索引方案，RaBitQ 性能领先 |
| **国内 + 海外 + 不想双云** | 开源 Milvus（DiskANN）或 Qdrant（量化） | 自建统一架构，但需投入运维成本 |

### 5.2 分阶段实施建议

**第一阶段：国内优先验证（1-2 周）**

- 在腾讯云 VectorDB 上开启 DiskFLAT/DiskANN 磁盘索引
- 验证内存节省效果和查询性能是否满足业务要求
- 评估 Recall 指标是否达标（建议目标 ≥95%）

**第二阶段：海外方案选定（2-4 周）**

- 如海外为硬性需求：启动阿里云 Milvus POC，验证 DiskANN+RaBitQ 在实际业务数据上的表现
- 如海外可暂缓：向腾讯云跟进海外磁盘索引上线时间表
- 如需完全自主可控：评估开源 Milvus 或 Qdrant 自建方案

**第三阶段：迁移实施（4-8 周）**

- 制定数据迁移方案（存量数据导入 + 增量双写）
- 重写接入层适配新 SDK
- 灰度切换 + 线上验证

### 5.3 关键风险提示

1. **双云架构复杂度**：国内腾讯云 + 海外阿里云意味着两套运维体系、两套监控告警、数据跨云同步等额外复杂度
2. **数据迁移一致性**：向量数据迁移需保证写入不丢、查询不乱，建议采用增量双写 + 对比验证策略
3. **开源方案运维成本**：Milvus 集群需管理 6+ 组件，Qdrant 单机简洁但扩展性受限，均需专职运维人员
4. **DiskANN 延迟可接受性**：磁盘索引 P99 延迟 5-40ms，对实时性要求极高的场景（如实时竞价/广告投放）不适用，但 RAG/语义搜索场景通常可接受（LLM 响应本身 500-2000ms）
